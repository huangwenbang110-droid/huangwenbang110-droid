# 云原生可观测 · 从自研 SDK 到 AI 可观测

七年间完整走过可观测体系的四代演进：自研 SDK → Agent 架构 → OpenTelemetry 统一 → AIOps / AI 可观测。
在数百应用、数千业务单元、数万节点、日均数十 TB 的规模上做过完整的工程落地。

技术栈：Java、Python。

---

## 演进线

| 阶段 | 做了什么 | 关键转折 |
|---|---|---|
| 自研 SDK | Octopus：指标 / 日志 / 调用链，从零构建 | 为什么当时的开源方案不够用 |
| Agent 架构 | Java / Python 双栈探针，从侵入式走向零侵入 | SDK 模式在规模化后的失效点 |
| 云原生可观测平台 | 覆盖指标 / 日志 / 链路 / 告警的完整平台 | 规模量级带来的架构约束 |
| OpenTelemetry 统一 | 协议与语义迁移，存量兼容 | 迁移的真实代价 |
| AIOps | 智能告警根因分析 + APM 智能助手 | 大模型在工程上的边界 |
| AI 可观测 | Token 成本治理与内容脱敏 | 为什么治理层不能放在采集层 |

## 开源项目

**ai-observability-guard** — 开发中

零侵入的 Java Agent，在 OTel Span 层为 Java AI 框架补上成本治理与内容脱敏；配一个 Starter 补上调用前的预算熔断与循环检测。

- 治理层挂 OTel 的 SpanProcessor 与 SpanExporter 装饰器，不增强任何框架类
- 一个实现覆盖 Spring AI 与 LangChain4j，对框架版本免疫
